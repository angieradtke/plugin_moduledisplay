# PLG_SYSTEM_MODULEDISPLAY – Display Modules by Component, View and Layout


## Overview

System plugin for Joomla 6. Extends module parameters with filtering based on the Component, View and Layout combination in which a module is displayed in the frontend – in addition to Joomla's regular menu assignment.

By default, Joomla only allows modules to be assigned to menu items. This plugin adds a more granular level: display can depend on the actually requested `option` (Component), `view` and the active Layout.

For example, a module can be displayed only on an article detail page – or only when that page uses a specific alternative Layout.

The desired combinations are selected per module from an automatically generated list.

Filtering is performed server-side and exclusively in the frontend (`onAfterCleanModuleList`). Modules without an active filter behave unchanged.

##  Requirements

* Joomla 6.0 or newer
* PHP 8.1 or newer

Both requirements are checked during installation.

##  Installation

1. Download `plg_system_moduledisplay.zip` (contents are directly in the ZIP root; there is no additional folder).
2. In Joomla: **System → Install → Extensions → Upload Package File**.
3. Enable the plugin under **System → Plugins → “System – Module Display Rules”**.

No separate global “Enabled” parameter is required – the Published status in the Plugin Manager is sufficient.

> **Updates:** Completely uninstall the plugin and install it again instead of overwriting it. Joomla caches PSR-4 namespaces in `administrator/cache/autoload_psr4.php`; otherwise, an old class version may remain active.

##  Configuration per Module

In the edit form of each module (**Content → Site Modules → [Open Module]**), the **“Display Rules”** section is available.

### View filter for this module

Default: **No** – the module remains unchanged. Filtering is activated only when set to **Yes**.

###  Display on

The Component-grouped multi-selection contains two types of entries for each View:

| Entry                 | Applies to                                           |
| --------------------- | ---------------------------------------------------- |
| `article`             | **all** pages of this View, regardless of the Layout |
| `article : my-layout` | only the `my-layout` Layout                          |

Both entries can be selected independently. Selecting only `article : my-layout` means the module is displayed exclusively there – the base View entry does not need to be selected as well.

Layouts are detected from the Component's own `tmpl/<view>/*.php` files and from template overrides under `templates/<template>/html/com_xxx/<view>/*.php`.

`default.php` is not listed because it is already covered by the View entry. Sub-templates containing an underscore according to Joomla conventions (`blog_item.php`, `default_articles.php`, etc.) are also excluded.


### Events

| Event                    | Purpose                                                                             |
| ------------------------ | ----------------------------------------------------------------------------------- |
| `onContentPrepareForm`   | Adds the additional fields to the module form (`com_modules.module`), backend only. |
| `onAfterCleanModuleList` | Filters the module list in the frontend before the modules are rendered.            |

Both use Joomla 6's typed event classes (`PrepareFormEvent`, `AfterCleanModuleListEvent`).

### Form Field

The field extends Joomla's `GroupedlistField` and only implements `getGroups()`. Rendering, escaping and storage are therefore handled entirely by Joomla core – no custom HTML and no custom JavaScript.

### Data Storage

Joomla stores the selection as an array of strings in the module parameter `moduledisplay_rules`:

```json
["com_content:article:", "com_content:article:my-layout"]
```

An empty Layout part acts as a placeholder for “any Layout”.

Rules from previous versions (objects with separate fields) are automatically converted when the form is opened and are still accepted during evaluation.

### Caching

The list of Views and Layouts is generated by scanning all Components and templates. The result is stored in the Joomla cache (group `plg_system_moduledisplay`) and additionally kept per request.

New Views, Layouts or overrides appear after clearing the cache under **System → Clear Cache**.

### Case Sensitivity

Layout names are preserved exactly as the filename defines them – `My-Layout.php` remains `My-Layout`.

On case-sensitive file systems such as Linux, normalizing the name would be problematic because Joomla would no longer find the file under its actual name.

Layout matching is case-insensitive at runtime, so both spellings match each other.

### Layout Resolution

The currently active Layout is determined in the following order:

1. URL parameter `&layout=...`
2. Response from another extension via the `onModuleDisplayResolveLayout` event
3. Layout configured on the record itself (Options → Alternative Layout). The location where a Component stores this setting is defined in the `LAYOUT_SOURCES` table – including both table and column, since articles store their parameters in `attribs`, while categories and other records use `params`.
4. Layout of the active menu item – but only if it actually points to the same Component, View and, for individual records, the same item.
5. Fallback: `default`

For alternative layouts, the plugin removes Joomla's stored template prefix (`isails:my-layout` → `my-layout`).

The URL parameter is therefore read as a string and validated afterwards. Using `getCmd()` would remove the colon and turn `isails:start` into `isailsstart`, which would not match the actual Layout.

### Extensibility: onModuleDisplayResolveLayout

Components that store their alternative Layout somewhere else – for example custom developments or third-party extensions – do not need to be added to `LAYOUT_SOURCES`.

Instead, they can listen to the `onModuleDisplayResolveLayout` event and provide the Layout themselves:

```php
use Joomla\Plugin\System\ModuleDisplay\Event\ResolveLayoutEvent;

public function onModuleDisplayResolveLayout(ResolveLayoutEvent $event): void
{
    if ($event->getOption() !== 'com_example') {
        return;
    }

    $id = $event->getId();

    // Determine the Layout using your own logic ...
    $event->addResult('my-layout');
}
```

The event is a typed, immutable class (`AbstractImmutableEvent` with `ResultAwareInterface`).

It provides `getOption()`, `getView()` and `getId()`. Responses are added using `addResult()`, which accepts strings only.

If an extension has nothing to contribute, it simply returns without adding a result.

The first usable response wins. The event is processed before the database lookup and can therefore deliberately override the standard detection.

Exceptions in listeners are caught so that an extension cannot break the page.

### Security Principles

* No Joomla core files are modified.
* No dynamic class loading based on request parameters.
* `option`, `view` and `layout` are validated using a regular expression before any use, including before constructing file paths (prevents path traversal).
* Database queries are parameterized (`bind` with `ParameterType::INTEGER`); the table name comes exclusively from the hard-coded `LAYOUT_SOURCES` table and never from the request.
* Filtering removes modules server-side from the module list rather than using CSS or JavaScript.

## Known Limitations

* Database-based Layout detection only covers the core Components listed in `LAYOUT_SOURCES`, because each Component stores its Layout setting differently. Other extensions can integrate via `onModuleDisplayResolveLayout`; without this integration, only URL and menu-item detection are available.
* Sub-templates are identified by an underscore in the filename. Custom partial Layouts without an underscore will therefore appear in the selection list.
* After creating a new Layout or override, the Joomla cache must be cleared for the new entry to appear in the selection list.

## Tests

The matching logic (`ModuleDisplay::matchesRules()`) is covered by unit tests. It determines whether a module should be displayed and had several bugs during development.

The tests are located in the source package under `tests/` and are not installed with the plugin.
